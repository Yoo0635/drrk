# `spec.md` 작성 규격

이 문서는 루트 `spec.md`를 작성하거나 수정할 때 따르는 양식과 작성 규칙이다. 저장소 정책은 `AGENTS.md`를 우선한다.

## Required Format

```markdown
# Spec

## Index
- 없음

## Goal
이번 작업으로 달성할 결과를 1-3줄로 적는다.

## Scope
- 포함: 이번 작업에서 바꿀 범위
- 제외: 의도적으로 다루지 않는 범위

## Design
- 변경 위치와 주요 흐름
- 필요한 데이터·API·모듈 경계
- 오류 및 예외 처리
- 결정사항
- 보류사항
- 남은 위험

## Test Plan
- 정상 동작 검증
- 주요 실패·경계 조건 검증

## Notes
- 요구사항의 모호함, 보류한 결정, 후속 작업
```

작업이 작으면 각 섹션은 1-3줄로 끝낸다. 작업이 커도 설계 문서는 구현 계획서가 아니므로 세부 단계까지 길게 풀지 않는다.

## Index Rules

`Index`는 문서 연결용이다.

- 부모 문서는 하위 문서 경로와 한 줄 요약만 적는다.
- 부모 문서에 하위 문서 내용을 반복하지 않는다.
- 하위 문서가 추가되거나 중요한 결정이 바뀌면 가장 가까운 부모 `memory.md`의 인덱스도 갱신한다.
- 현재 저장소는 루트 `spec.md` 하나만 사용하므로 하위 문서가 없으면 `- 없음`으로 적는다.

예시:

```md
## Index
- `backend/spec.md`: 백엔드 변경 범위 요약
- `frontend/spec.md`: 프론트엔드 변경 범위 요약
```

## Writing Rules

- 요구사항이 불명확하면 추측하지 말고 `Notes`에 명시한다.
- 기존 패턴을 우선 따르고, 새 구조는 필요한 경우에만 제안한다.
- 공용 모듈에는 둘 이상의 실행 모듈에서 함께 쓰는 것만 둔다.
- 한 모듈에서만 쓰는 코드는 해당 모듈 안에 둔다.
- 설계에는 파일명, 클래스명, API 경로처럼 구현자가 바로 찾을 수 있는 이름을 쓴다.
- “추후 고려”, “확장 가능” 같은 문장은 실제 후속 작업이 정해졌을 때만 쓴다.

## Commit Rules

커밋은 추적과 디버깅이 쉽도록 잘게 나눈다.

- 서로 다른 목적의 변경은 같은 커밋에 섞지 않는다.
- 설계 문서, 테스트, 구현, 리팩터링은 가능하면 별도 커밋으로 나눈다.
- 한 커밋은 나중에 되돌리거나 원인을 추적할 수 있는 단위여야 한다.
- 동작 변경 없는 포맷팅이나 정리는 기능 변경 커밋과 분리한다.
- 커밋 메시지는 `AGENTS.md`의 Conventional Commits 규칙에 따라 한글로 간결하고 명확하게 작성한다.

예시:

```text
docs: 댓글 생성 설계 추가
test: 댓글 생성 서비스 테스트 추가
feat: 댓글 생성 API 구현
refactor: 댓글 조회 로직 정리
```

## Good Example

```md
# Spec

## Index
- 없음

## Goal
사용자가 게시글에 댓글을 작성할 수 있게 한다.

## Scope
- 포함: 댓글 생성 API, 댓글 저장, 서비스 테스트
- 제외: 댓글 수정, 댓글 삭제, 알림 연동

## Design
- 댓글 생성 API는 게시글 단위 하위 리소스로 둔다.
- 댓글은 게시글 ID와 작성자 ID를 필수로 가진다.
- 게시글이 없으면 404를 반환한다.
- 인증되지 않은 요청은 기존 인증 실패 흐름을 따른다.

## Test Plan
- 게시글이 존재하면 댓글 생성 성공
- 게시글이 없으면 404
- 인증되지 않으면 실패

## Notes
- 알림 연동은 후속 작업에서 처리한다.
```

## Bad Example

```md
## Design
댓글 기능은 사용자의 소통을 강화하고 서비스 참여도를 높인다.
나중에 좋아요, 신고, 대댓글, 알림, 관리자 제재도 가능하게 확장할 수 있다.
전체적으로 확장성 있는 구조로 잘 만든다.
```

문제:

- 구현 위치가 없다.
- 이번 범위가 없다.
- 검증 기준이 없다.
- “확장성”만 있고 실제 결정이 없다.

## Completion Check

`spec.md` 작성 후 아래를 확인한다.

- 이번 작업과 무관한 설명을 제거했는가?
- 포함/제외 범위가 분리되어 있는가?
- 구현자가 바꿀 위치를 찾을 수 있는가?
- 테스트 계획이 실제 동작 검증으로 이어지는가?
- 모호한 표현이 결정사항 또는 보류사항으로 정리되었는가?
