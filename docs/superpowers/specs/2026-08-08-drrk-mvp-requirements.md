# 드르륵 백엔드 MVP 요구사항 명세서

| 항목 | 내용 |
|---|---|
| 문서 상태 | Draft v1.1 |
| 작성일 | 2026-08-08 |
| 프로젝트 | 캐리어 소리 기반 철도 혼잡 예측 서비스 |
| 구현 범위 | 모델 출력 이벤트 수신 이후의 백엔드·서비스 MVP |
| 기준 자료 | 해커톤 참가 신청서의 프로젝트 기획서 및 팀 합의사항 |

## 1. 목적

외부 모델이 생성한 캐리어 통과 이벤트를 백엔드가 수신한 시점부터 이벤트를 검증·저장·집계하고, 항공 운항정보 및 철도 운행정보와 결합하여 공항철도 승강장의 수하물 혼잡 정보를 제공한다. 원본 음향 처리와 AI 모델 실행은 이 문서의 범위에 포함하지 않는다.

## 2. MVP 범위 및 전제

| ID | 구분 | 명세 |
|---|---|---|
| SCP-001 | 입력 경계 | 백엔드의 시작점은 외부 모델이 `POST /api/v1/events`로 이벤트 배열을 전송하는 시점이다. |
| SCP-002 | 백엔드 책임 | 백엔드는 수신 이벤트의 유효성 검증, 중복 제거, 저장, 집계, 조회와 서비스 화면 제공을 담당한다. |
| SCP-003 | 범위 제외 | 원본 WAV 수집, 신호 전처리, 특징 추출, AI 추론, 클래스 선택, 이벤트 후처리와 모델 평가는 외부 모델 시스템의 책임으로 둔다. |
| SCP-004 | 센서 범위 | MVP는 단일 설치 지점에서 전달되는 이벤트를 처리하되 `sensor_id`로 설치 지점을 구분한다. |
| SCP-005 | 수량 의미 | 백엔드는 모델이 전달한 `count`를 그대로 사용하며, `count=3`은 `3개 이상`으로 해석한다. |
| SCP-006 | 예측 범위 | 수신 이벤트, 항공 도착정보, 공항철도 시간표를 이용하여 10분 단위 승강장 도착 분포를 생성한다. |
| SCP-007 | 안내 범위 | 여객 안내 화면과 공개형 운영 대시보드를 제공한다. |
| SCP-008 | 호차 안내 | 실제 호차별 잔여 공간이 아니라 예상 수하물 유입이 적은 승강장 구역 및 대응 호차를 추천한다. |
| SCP-009 | 인증 정책 | 한 회원은 이메일, Google, Kakao 중 하나의 로그인 방식만 가진다. 동일 이메일의 다른 방식 가입은 차단한다. |
| SCP-010 | 운영자 권한 | MVP 사용자 테이블에는 역할을 저장하지 않는다. 운영 대시보드는 해커톤 데모에서 공개 화면으로 제공한다. |
| SCP-011 | 외부 데이터 | 외부 API 연결이 불가능한 데모 환경에서는 동일 스키마의 고정 샘플 데이터를 사용한다. |

| 우선순위 | 의미 |
|---|---|
| P0 | MVP 완료와 핵심 시연에 필수인 요구사항 |
| P1 | 시간이 허용될 때 구현하는 보조 요구사항이며 미구현이어도 MVP 완료로 판단 |

## 3. 사용자 및 외부 주체

| 주체 | 설명 | 주요 행위 |
|---|---|---|
| 여객 | 공항철도를 이용하려는 사용자 | 회원가입, 로그인, 다음 열차 혼잡 확인, 추천 위치 확인 |
| 역 운영자 | 혼잡 상황을 확인하는 현장 담당자 | 시간대별 유입량, 예측 분포, 센서 상태 확인 |
| 모델 출력 시스템 | 완성된 이벤트 레코드를 생성하는 외부 시스템 | 이벤트 배열을 백엔드에 전송 |
| 백엔드 계산 모듈 | 수신 이벤트와 항공·철도 데이터를 결합하는 서버 기능 | 잔여 물량과 승강장 도착 분포 산출 |
| 외부 데이터 제공자 | 항공 및 철도 데이터를 제공하는 시스템 | 운항정보와 시간표 제공 |

## 4. 기능 요구사항

### 4.1 회원 및 인증

| ID | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---:|---|
| AUTH-001 | 사용자는 이메일, 8~64자의 비밀번호, 2~20자의 닉네임으로 가입할 수 있어야 한다. | P0 | 유효한 입력과 완료된 이메일 인증으로 `LOCAL` 사용자가 생성된다. |
| AUTH-002 | 이메일 가입 전에 SMTP 인증을 완료해야 한다. | P0 | 인증번호가 일치하고 만료되지 않은 경우에만 가입이 성공한다. |
| AUTH-003 | 이메일 인증번호는 Redis에 저장하고 5분 후 만료해야 한다. | P0 | 5분이 지난 인증번호로 검증을 요청하면 실패한다. |
| AUTH-004 | 비밀번호 확인 값은 서버에서 일치 여부만 확인하고 저장하지 않아야 한다. | P0 | 사용자 데이터와 로그에 비밀번호 확인 값이 남지 않는다. |
| AUTH-005 | 비밀번호는 단방향 해시로 저장해야 한다. | P0 | DB와 애플리케이션 로그에 평문 비밀번호가 존재하지 않는다. |
| AUTH-006 | 사용자는 Google 계정으로 가입하고 로그인할 수 있어야 한다. | P0 | 검증된 Google ID 토큰의 `sub`로 동일 사용자를 식별한다. |
| AUTH-007 | 사용자는 Kakao 계정으로 가입하고 로그인할 수 있어야 한다. | P0 | Kakao 사용자 정보 API의 서비스 사용자 ID로 동일 사용자를 식별한다. |
| AUTH-008 | 소셜 로그인에서 이메일이 없거나 유효·인증 상태가 아니면 가입을 거절해야 한다. | P0 | 이메일 조건을 충족하지 않는 응답으로 신규 사용자가 생성되지 않는다. |
| AUTH-009 | 이메일은 앞뒤 공백 제거와 소문자 변환 후 전체 사용자에서 유일해야 한다. | P0 | 다른 로그인 방식이라도 같은 정규화 이메일로 두 번째 사용자를 생성할 수 없다. |
| AUTH-010 | 기존 이메일이 다른 로그인 방식으로 존재하면 자동 연결하지 않고 가입을 차단해야 한다. | P0 | 충돌 응답에 기존 로그인 방식이 포함되고 사용자 행은 추가되지 않는다. |
| AUTH-011 | 로그인 성공 시 서비스 전용 인증 토큰을 발급해야 한다. | P0 | 외부 제공자의 액세스 토큰 대신 서비스 토큰으로 보호 API를 호출할 수 있다. |
| AUTH-012 | 닉네임 중복을 허용해야 한다. | P1 | 같은 닉네임을 가진 서로 다른 사용자를 생성할 수 있다. |

### 4.2 센서 이벤트 수집

백엔드는 아래 레코드를 모델 출력의 고정 입력 계약으로 사용한다.

| 필드 | 자료형 | 필수 여부 | 백엔드 검증 및 사용 규칙 |
|---|---|---:|---|
| `schema_version` | string | 필수 | 지원하는 이벤트 스키마 버전인지 확인한다. 예: `1.0.0` |
| `sensor_id` | string | 필수 | 비어 있을 수 없으며 설치 지점을 식별하는 값으로 사용한다. |
| `event_id` | UUID | 필수 | 이벤트 중복 제거 키로 사용한다. |
| `t_onset` | UTC datetime | 필수 | 통과 시작 시각이며 밀리초 정밀도의 ISO 8601 형식을 사용한다. |
| `t_offset` | UTC datetime | 필수 | 통과 종료 시각이며 `t_onset`보다 빠를 수 없다. |
| `count` | integer | 필수 | 1~3만 허용하고 3은 3개 이상으로 표시한다. |
| `count_expected` | float | 필수 | 0 이상의 집계용 기대값이며 10분 구간 합산에 사용한다. |
| `direction` | enum | 필수 | `outbound`, `inbound`, `unknown`만 허용한다. |
| `speed_mps` | float 또는 null | 선택 | 값이 있으면 0 이상이어야 하며 평균 통과 속도 집계에 사용한다. |
| `confidence` | float | 필수 | 0~1 범위만 허용하고 평균 신뢰도 집계에 사용한다. |
| `model_version` | string | 필수 | 비어 있을 수 없으며 결과 추적용으로만 저장한다. |

| ID | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---:|---|
| EVT-001 | 백엔드는 `POST /api/v1/events`로 센서 이벤트 배열을 수신해야 한다. | P0 | 유효한 이벤트 1개 이상을 포함한 배열 요청이 성공한다. |
| EVT-002 | 각 이벤트는 `schema_version`, `sensor_id`, `event_id`, `t_onset`, `t_offset`, `count`, `count_expected`, `direction`, `speed_mps`, `confidence`, `model_version`을 포함해야 한다. | P0 | 필수 필드 누락 시 해당 이벤트가 유효성 검증 오류로 거절된다. |
| EVT-003 | `event_id`는 전체 이벤트에서 유일해야 한다. | P0 | 같은 이벤트를 재전송해도 한 번만 저장되고 한 번만 집계된다. |
| EVT-004 | `t_offset`은 `t_onset`보다 빠를 수 없다. | P0 | 종료 시각이 시작 시각보다 빠른 이벤트는 저장되지 않는다. |
| EVT-005 | `count`는 1~3, `confidence`는 0~1 범위여야 한다. | P0 | 허용 범위를 벗어난 요청은 저장되지 않는다. |
| EVT-006 | `direction`은 `inbound`, `outbound`, `unknown` 중 하나여야 한다. | P0 | 정의되지 않은 방향 값은 유효성 검증 오류가 된다. |
| EVT-007 | 속도 추정에 실패한 경우 `speed_mps`의 `null`을 허용해야 한다. | P0 | 속도가 없는 정상 이벤트가 저장된다. |
| EVT-008 | 이벤트 API는 위 입력 계약 외의 원본 음성 파일을 입력으로 받지 않아야 한다. | P0 | 파일 또는 음성 바이너리가 포함된 요청은 처리 대상에서 제외되고 저장소에 음성 데이터가 생성되지 않는다. |
| EVT-009 | 서버 수신 시각을 이벤트에 기록해야 한다. | P1 | 모든 저장 이벤트에 `received_at`이 존재한다. |

### 4.3 집계 및 외부 데이터

| ID | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---:|---|
| DAT-001 | 센서 이벤트를 센서별·방향별 10분 구간으로 집계해야 한다. | P0 | 동일 입력 데이터에 대해 구간별 실제 수량 합계가 재현된다. |
| DAT-002 | 집계 결과에 실제 수량, 기대 수량, 평균 속도, 평균 신뢰도를 제공해야 한다. | P0 | 집계 API가 네 값을 각 시간 구간에 반환한다. |
| DAT-003 | 항공편의 편명, 출발지, 예정·변경·실제 도착 시각, 기종을 수집해야 한다. | P0 | 외부 API 또는 샘플 데이터가 공통 내부 형식으로 변환된다. |
| DAT-004 | 제공 가능한 경우 수하물 수취대, 입국장 게이트, 대기 인원을 함께 수집해야 한다. | P1 | 값이 없는 경우에도 필수 항공 데이터 처리가 실패하지 않는다. |
| DAT-005 | 기종별 좌석 수 매핑으로 항공편별 최대 예상 여객 규모를 계산해야 한다. | P0 | 동일 기종과 운항정보에 대해 같은 예상 규모가 산출된다. |
| DAT-006 | 공항철도 열차의 출발 시각, 승강장, 호차 위치 매핑을 관리해야 한다. | P0 | 특정 시각의 다음 열차와 추천 승강장 구역을 조회할 수 있다. |
| DAT-007 | 외부 데이터 연결 실패 시 고정 샘플 데이터로 데모를 지속해야 한다. | P0 | 외부 API를 차단해도 예측 및 화면 시연이 가능하다. |

### 4.4 혼잡 예측

| ID | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---:|---|
| PRD-001 | 관측된 캐리어 수량과 항공편별 예상 총량을 비교하여 잔여 수하물 물량을 추정해야 한다. | P0 | 예상 총량에서 누적 관측량을 반영한 0 이상의 잔여량이 산출된다. |
| PRD-002 | 입국장 출구에서 승강장까지의 예상 이동 시간을 적용하여 10분 단위 도착 분포를 생성해야 한다. | P0 | 입력 시각과 이동 시간 변경이 예측 구간에 반영된다. |
| PRD-003 | 여객 수와 수하물 점유 가중치를 결합하여 혼잡 단계를 산출해야 한다. | P0 | 같은 여객 수에서도 수하물 예상량이 증가하면 혼잡도가 낮아지지 않는다. |
| PRD-004 | 혼잡도는 최소 `여유`, `보통`, `혼잡`의 세 단계로 제공해야 한다. | P0 | 모든 정상 예측 결과가 세 단계 중 하나를 포함한다. |
| PRD-005 | 음향 센서 데이터가 없을 때 항공 도착정보와 철도 시간표만으로 기본 예측을 생성해야 한다. | P0 | 센서 입력을 중단해도 예측 API가 기본 예측 결과를 반환한다. |
| PRD-006 | 센서 기반 예측과 기본 예측을 구분해야 한다. | P0 | 예측 결과에 `SENSOR_FUSION` 또는 `SCHEDULE_ONLY` 모드가 표시된다. |
| PRD-007 | 예측 결과에 기준 시각, 대상 열차, 시간 구간, 예상 유입량, 혼잡 단계, 계산 버전을 포함해야 한다. | P0 | 저장 및 조회되는 모든 예측 결과에 추적 필드가 존재한다. |
| PRD-008 | 엘리베이터 예상 이용량은 예측 수하물 유입량과 설정 가능한 이용 비율로 계산해야 한다. | P1 | 이용 비율 변경 시 예상 이용량이 동일 계산식에 따라 변경된다. |

### 4.5 여객 안내 화면

| ID | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---:|---|
| PSG-001 | 여객 화면은 현재 시각 기준 다음 공항철도 열차를 표시해야 한다. | P0 | 시간표에 따라 가장 가까운 미출발 열차가 표시된다. |
| PSG-002 | 대상 열차의 예상 수하물 혼잡 단계와 예상 유입량을 표시해야 한다. | P0 | 최신 예측 결과의 혼잡 단계와 수량이 화면에 표시된다. |
| PSG-003 | 예상 유입이 적은 추천 호차 또는 승강장 구역을 행동형 문구로 안내해야 한다. | P0 | 화면에 추천 위치와 이동 방향이 함께 표시된다. |

## 9. 완료 조건

다음 조건을 모두 만족하면 MVP 요구사항 구현이 완료된 것으로 본다.

1. P0 기능 요구사항이 모두 구현되고 핵심 인수 시나리오가 통과한다.
2. 센서 이벤트 중복 제거, 10분 집계, 혼잡 예측, 장애 시 기본 예측이 시연된다.
3. 여객 화면과 운영 대시보드에서 동일한 최신 예측을 확인할 수 있다.
4. 이메일·Google·Kakao 가입 정책과 전체 이메일 유일성이 검증된다.
5. 백엔드가 정의된 이벤트 레코드만 입력으로 받고 원본 음성이나 모델 내부 데이터를 저장하지 않음을 확인한다.
6. MVP 제외 범위가 구현 범위에 섞이지 않는다.
